# Worked example: matching a payment to an invoice

The model is [matching.als](matching.als). Everything
below is its actual output from Alloy 6.2.0.

The question is the one that matters for any matcher that moves money. Can the
rule ever link a payment to a record that is not the one the sender was paying
for? A false negative leaves the payment for a human to review. A false positive
posts money against the wrong record, and nobody finds out.

## Step 1: state the property in one sentence

A match is never wrong.

That sentence needs a notion of the right answer, which no table in the
database has. So the model gets one.

```alloy
sig Payment {
  reportedAccount : one Account,
  reportedRef     : lone Ref,
  truth           : lone Invoice   // the invoice this payment is really for
}
```

`truth` is `lone` rather than `one` on purpose. A payment can arrive for an
invoice we never issued, and that case turns out to matter.

## Step 2: model the smallest thing that can break it

Three identifiers and two record types. No dates, no amounts, no names, because
the rule under test does not read them.

```alloy
sig Invoice {
  vendor  : one Vendor,
  account : one Account,
  ref     : lone Ref
}
```

One fact says what a sender does, which is echo back the identifiers printed on
the invoice being paid.

```alloy
fact payment_echoes_the_invoice {
  all p : Payment | some p.truth implies {
    p.reportedAccount = p.truth.account
    p.reportedRef     = p.truth.ref
  }
}
```

Then the rule itself, written as a derived relation so the property can be
stated about it.

```alloy
fun candidates [p : Payment] : set Invoice {
  { i : Invoice | some p.reportedRef and i.ref = p.reportedRef and i.account = p.reportedAccount }
}

fun matched_v1 : Payment -> Invoice {
  { p : Payment, i : Invoice | i in candidates[p] }
}

pred sound [m : Payment -> Invoice] {
  all p : Payment, i : Invoice | p->i in m implies i = p.truth
}
```

## Step 3: run the check and read the story

```
00. check v1_is_sound              0    1/1     SAT
```

SAT on a `check` means a counterexample exists. Here it is.

```
this/Invoice={Invoice$0, Invoice$1}
this/Invoice<:vendor={Invoice$0->Vendor$1, Invoice$1->Vendor$0}
this/Invoice<:account={Invoice$0->Account$0, Invoice$1->Account$0}
this/Invoice<:ref={Invoice$0->Ref$0, Invoice$1->Ref$0}
this/Payment<:truth={Payment$0->Invoice$0}
skolem $sound_p={Payment$0}
skolem $sound_i={Invoice$1}
```

In words: two invoices sit on the same account, from two different vendors,
carrying the same reference number. The payment really belongs to the first
invoice. The rule links it to the second one as well. That is a false positive,
and it is the collision case that appears in real data whenever a reference
number is chosen by the counterparty rather than generated centrally.

The solver found this at a bound of 4 atoms per signature, in well under a
second.

## Step 4: change the rule, not the check

The fix is to decline instead of guessing.

```alloy
fun matched_v2 : Payment -> Invoice {
  { p : Payment, i : Invoice | i in candidates[p] and one candidates[p] }
}
```

```
01. check v2_is_sound              0       UNSAT
```

UNSAT means no counterexample exists inside the bound. Note what the assertion
actually says.

```alloy
assert v2_is_sound { no_foreign_refs implies sound[matched_v2] }
```

## Step 5: find out what the result depends on

`no_foreign_refs` is an assumption about the world, written down as a predicate
so it appears in the result.

```alloy
pred no_foreign_refs {
  all p : Payment | no p.truth implies no (p.reportedRef & Invoice.ref)
}
```

It says a reference number of ours never appears on a payment for an invoice we
did not issue. Drop it and the rule is unsound again.

```
02. check v2_is_sound_without_assumptions     0    1/1     SAT
```

The counterexample is a payment for an invoice that was never ours, whose
reference number happens to equal one of ours. The uniqueness rule does not
help, because there is exactly one candidate and it is still the wrong record.

This is the real output of the exercise. The rule is sound if and only if that
assumption holds, and now it is written where a reviewer can argue with it. If
reference numbers come from the counterparty, the assumption is false and the
rule needs another discriminating field. If they are generated by us and never
reused, it is true and the check stands.

## Step 6: measure what soundness cost

```alloy
assert v2_matches_every_real_pair {
  no_foreign_refs implies
    all p : Payment | (some p.truth and some p.truth.ref) implies p.truth in p.matched_v2
}
```

```
03. check v2_matches_every_real_pair     0    1/1     SAT
```

The rule does drop real pairs, and the counterexample says exactly when: the
reference number is ambiguous. Adding the uniqueness assumption confirms that
this is the only case it drops.

```
04. check v2_matches_every_real_pair_when_refs_are_unique     0       UNSAT
```

So the trade is stated precisely. The rule never links the wrong record, and it
gives up exactly the payments whose reference number is shared. Those payments
are the human review queue, and their volume is now a measurable thing rather
than a guess.

## Step 7: prove the rule can still fire

```alloy
run v2_can_match { some matched_v2 } for 4 expect 1
```

```
05. run   v2_can_match             0    1/1     SAT
```

Without this line, a rule that matched nothing at all would pass every check
above.

## What to take from this

- The model is 97 lines and the whole file checks in under a second.
- The first counterexample was a bug in the rule. The second was a missing
  assumption about the outside world. Both are things a code review can miss and
  a test suite would only find if someone had already thought of the case.
- Nothing here proves the production matcher is correct. It proves things about
  the rule as written in the model. Keeping the two in step is the real
  discipline, and [other-tools.md](../other-tools.md) covers ways to tie a model to
  running code.
- The next thing to model is whichever field you add to the rule next. Every new
  discriminator is a new soundness question.
